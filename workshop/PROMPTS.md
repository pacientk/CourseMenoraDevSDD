# Промпты курса — копировать и вставлять

Все команды и промпты встречи по шагам. Блок с пометкой **терминал** выполняется в
обычном терминале, блок с пометкой **Claude** вставляется в сессию Claude Code.

Отстали или что-то пошло не так — в конце каждого шага есть раздел «Если не
получилось» с готовым запасным вариантом.

## Догнать группу

Сильно отстали — перейдите на готовое состояние проекта после нужного шага.

**терминал**

```sh
npm run catchup          # список контрольных точек
npm run catchup -- 4     # перейти к точке 4
```

| Точка | Состояние | Продолжать с |
|---|---|---|
| 1 | Агент `react-engineer` создан | шаг 3 |
| 2 | SPEC-001 закрыта и влита в `main` | шаг 4 |
| 3 | SPEC-002: эпик утверждён, задачи и план готовы | шаг 5, волна 1 |
| 4 | Волна 1 исполнена | шаг 5, волна 2 |
| 5 | Волна 2 исполнена | шаг 5, волна 3 |
| 6 | Волна 3 исполнена, страница работает | шаг 6 |
| 7 | Ревью пройдено, замечания исправлены | шаг 7 |
| 8 | SPEC-002 закрыта и влита в `main` | — |

Ваша работа не пропадёт: команда сохраняет её в ветке `backup/…` и, если были
незакоммиченные правки, в `git stash`. После перехода перезапустите сессию Claude
Code: `/exit`, затем `claude`.

## Шаг 0 — Подготовка (до встречи)

**терминал**

```sh
git clone https://github.com/pacientk/CourseMenoraDevSDD.git
cd CourseMenoraDevSDD
npm install
npm run doctor
```

`npm run doctor` должен закончиться строкой «Готово к работе». Пункты `[INFO]` про
агента и плагин — нормальны: их делаем на встрече.

## Шаг 1 — Запуск и подключение плагина ревьюера

**терминал** — из корня репозитория

```sh
claude
```

**Claude** — по одной команде

```
/plugin marketplace add ./tools/claude-marketplace
```

```

```

Затем перезапустите сессию: `/exit`, снова `claude`. Проверка — наберите `/reviewer`
и убедитесь, что в подсказке есть `/reviewer:review`.

**Claude** — знакомство с проектом

```
Прочитай CLAUDE.md, docs/architecture/conventions.md и .claude/skills/sdd/SKILL.md.
Ответь коротко, списком:
1) какие гейты есть в проекте и какой командой закрывается каждый;
2) кто пишет код, кто его проверяет и почему это разные роли;

```


Не работает и это — возьмите запасного ревьюера (он вызывается не командой, а
просьбой, см. шаг 6):

```sh
cp workshop/fallback/agents/code-reviewer.md .claude/agents/code-reviewer.md
```

## Шаг 2 — Создаём агента-исполнителя по аналогии

У нас есть готовый агент для React Native: `workshop/reference/rn-engineer.md`. Просим
Claude сделать по его образцу агента для этого проекта.

**Claude**

```
Создай агента-исполнителя для этого проекта по образцу существующего.

Образец: workshop/reference/rn-engineer.md — агент для React Native, который
работает со стандартами из каталога standards/ и профилем проекта.

Нужно: .claude/agents/react-engineer.md — агент для этого проекта (React web, Vite,
TypeScript, Vitest).

Сохрани из образца:
- структуру шагов 0–4: загрузка правил → методологический гейт → реализация →
  Definition of Done → hand-off;
- формат frontmatter и описание с примерами вызова;
- запреты: не ослаблять правила ради зелёного результата, не пропускать гейт молча,
  не чинить то, что вне границ задачи;
- обработку находок ревью с идентификаторами F-1, F-2.

Замени:
- источники правил в шаге 0: вместо standards/ и PROJECT-PROFILE — CLAUDE.md и
  docs/architecture/conventions.md этого проекта, плюс docs/design/README.md;
- правила React Native в шаге 2 — на правила из docs/architecture/conventions.md
  с меткой [Review]: то, что линт не ловит;
- гейты в шаге 3 — на команды из таблицы в CLAUDE.md;
- формат hand-off — на шаблон .claude/skills/sdd/templates/handoff.md.

Убери: всё про React Native, симулятор, темы, память агента.

Добавь:
- в шаг 1: агент меняет файлы только в пределах Scope paths своей задачи и не
  редактирует plan.md и review.log.md;
- в шаг 3: правило для параллельной волны — тесты только по своим путям, ошибки в
  чужих файлах не чинить, а сообщать в hand-off;
- в шаг 2: файлы создаются и правятся инструментами Write и Edit, не через bash.

Во frontmatter: name: react-engineer, model: sonnet, color: green, без поля memory.
Пиши на русском. Сначала покажи таблицу «что взято из образца / что заменено / что
убрано», затем сразу запиши файл — подтверждения не жди.
```

Claude спросит разрешение на запись в `.claude/agents/` — согласитесь: каталог
`.claude` защищён, и правки в нём всегда подтверждаются вручную.

Проверка: перезапустите сессию (`/exit`, `claude`), наберите `/agents` — в списке
должен быть `react-engineer`.

**Claude** — агент теперь часть проекта, фиксируем

```
Закоммить нового агента в main: chore: add react-engineer agent
```

### Если не получилось

```sh
cp workshop/fallback/agents/react-engineer.md .claude/agents/react-engineer.md
```

## Шаг 3 — SPEC-001: small spec от чтения до работающей страницы

Спека уже написана и утверждена: `docs/specs/SPEC-001-app-shell/spec.md`. Откройте её
и прочитайте разделы 3, 4 и 5 — цель, границы, критерии приёмки.

**Claude** — исполнение (гейт G4)

```
/sdd run SPEC-001 --commit
```

Пока агент работает — смотрим на анатомию спеки на слайде.

**терминал** — второе окно, проверка в браузере

```sh
npm run dev
```

Откройте `http://localhost:5173`: адрес должен смениться на `/customers/1`, в шапке —
три пункта меню.

**Claude** — где мы находимся

```
/sdd status
```

**Claude** — закрываем SPEC-001 и возвращаемся в main

```
SPEC-001 проверена в браузере. Закрой её коротким путём: проставь статус done в
spec.md, допиши строку в «Журнал исполнения» и запись в docs/release-notes.md,
закоммить, затем перейди в main и
влей ветку spec/001-app-shell (--no-ff). Независимое ревью и security для этой
спеки на курсе пропускаем — запиши это в «Журнал исполнения» одной строкой с
причиной «экономия времени на встрече».
```

### Если не получилось

Агент застрял или гейт красный больше двух попыток:

```

Ничего не исправляй, пока я не отвечу.
```

## Шаг 4 — SPEC-002: эпик → задачи → план

Вводная от продукта лежит в `workshop/briefs/SPEC-002-customer-profile.md`. Прочитайте
её: это сырьё, а не спека.

**Claude** — эпик (гейт G0 → G1)

```
/sdd epic customer-profile

Бриф: workshop/briefs/SPEC-002-customer-profile.md
Дизайн: docs/design/customer-360.png и docs/design/README.md
Номер спеки: SPEC-002.
Уточняющих вопросов не задавай: чего нет в брифе — запиши в «Открытые вопросы».
После записи файла покажи таблицу самопроверки и список критериев приёмки.
```

**Проверяем эпик — 3 минуты, это гейт G1.** Откройте
`docs/specs/SPEC-002-customer-profile/epic.md` и ответьте себе на четыре вопроса:

1. Можно ли по каждому критерию приёмки сказать «выполнено» или «не выполнено»?
2. Есть ли критерий про поля `password`, `ssn`, `bank` — что они не попадают на экран?
3. Есть ли критерии на загрузку, ошибку, «не найдено», пустой список?
4. Непустой ли раздел «Не входит»?

Всё так — **сами** замените в таблице Meta `draft` на `approved` и сохраните файл.
Что-то не так — попросите Claude исправить конкретный пункт и проверьте снова.

**Claude** — задачи (гейт G2)

```
/sdd tasks SPEC-002

Не больше пяти задач. Слой данных и общие UI-элементы должны исполняться
параллельно; виджеты — параллельно на следующем шаге; сборка страницы — последней.
Общий словарь строк src/shared/i18n/he.ts правит только одна задача.
```

Посмотрите на индекс задач и граф: согласны с нарезкой?

**Claude** — план (гейт G3)

```
/sdd plan SPEC-002
```

**Claude** — фиксируем документы

```
Создай ветку spec/002-customer-profile и закоммить документы спеки:
docs(SPEC-002): epic, tasks, plan
```

### Если не получилось

Эпик или задачи получились слабыми, а время идёт — возьмите эталон:

```sh
mkdir -p docs/specs && cp -r workshop/golden/SPEC-002-customer-profile docs/specs/
```

Эталонный эпик лежит в статусе `draft`: прочитайте критерии приёмки и утвердите его
сами — гейт G1 никто не отменял.

## Шаг 6 — Независимое ревью и цикл исправлений

**Claude** — раунд 1 (гейт G5). Ревьюер работает в отдельном контексте и ничего не
меняет в проекте.

```
/reviewer:review задача: docs/specs/SPEC-002-customer-profile/epic.md
```

Прочитайте отчёт: вердикт, таблицу критериев приёмки, находки `F-1…`.

**Claude** — исправления по отчёту

```
/sdd fix SPEC-002
```

Оркестратор запишет раунд в `review.log.md`, передаст находки агенту
`react-engineer`, перепроверит гейт и выдаст готовую команду повторного ревью.

**Claude** — раунд 2 (подставьте команду, которую выдал `/sdd fix`; обычно такая)

```
/reviewer:review re-review: предыдущие замечания — docs/specs/SPEC-002-customer-profile/review.log.md, раунд 1; задача: docs/specs/SPEC-002-customer-profile/epic.md
```

**Claude** — записать итог раунда 2

```
/sdd fix SPEC-002
```

Вердикт `APPROVED` — гейт закрыт. Снова `CHANGES REQUESTED` — лимит двух раундов
исчерпан: оркестратор остановится и спросит решение у вас. Это правильное поведение.

**Claude** — фиксируем

```
Закоммить исправления по ревью: fix(SPEC-002): review round 1 findings
```

### Если не получилось

Используете запасного ревьюера (шаг 1) — вместо `/reviewer:review` пишите:

```
Запусти агента code-reviewer. Задача: docs/specs/SPEC-002-customer-profile/epic.md.
Объём: текущая ветка против main. Сам отчёт не редактируй и код не исправляй —
покажи мне отчёт ревьюера как есть.
```

**Claude** — security-ревью изменений ветки (гейт G6)


**Claude** — запись результата и закрытие спеки (гейты G7 и G8)

```

Результат /security-review возьми из этого разговора и запиши в review.log.md.
```

**терминал** — «деплой»: собранное приложение, как оно уйдёт на сервер (гейт G9)

```sh
npm run build
npm run preview
```

Откройте адрес из вывода (`http://localhost:4173`) и пройдите ручной чек-лист из
отчёта `/sdd close`. Без сети: `npm run preview:offline`.

**Claude** — слияние

```
Закоммить закрытие спеки: docs(SPEC-002): close, release notes.
Затем перейди в main и влей ветку spec/002-customer-profile (--no-ff). Не пушь.
```

**Claude** — что осталось в репозитории

```
/sdd status
```

### Если не получилось

`/security-review` не может определить базу для сравнения (нет `origin/HEAD`):

```
Проведи security-ревью изменений ветки spec/002-customer-profile относительно main.
Проверь по docs/architecture/conventions.md § 7: белый список полей ответа API,
отсутствие персональных данных в логах, проверку идентификатора и адреса картинки,
отсутствие dangerouslySetInnerHTML и eval, отсутствие секретов в репозитории.
Для каждой находки укажи файл, строку, сценарий атаки и уровень. Код не изменяй.
```

## Шпаргалка

| Что | Команда |
|---|---|
| Где мы находимся | `/sdd status` |
| Создать small spec | `/sdd small <slug>` + бриф |
| Создать эпик | `/sdd epic <slug>` + бриф |
| Задачи / план | `/sdd tasks SPEC-NNN` · `/sdd plan SPEC-NNN` |
| Исполнить (одна волна за вызов) | `/sdd run SPEC-NNN --commit` |
| Независимое ревью | `/reviewer:review задача: <путь к спеке>` |
| Исправить по отчёту | `/sdd fix SPEC-NNN` |
| Security | `/security-review` |
| Закрыть спеку | `/sdd close SPEC-NNN` |
| Все гейты локально | `npm run validate` · `npm run release:check` |
| Догнать группу | `npm run catchup` |
| Список агентов / плагинов | `/agents` · `/plugin` |
