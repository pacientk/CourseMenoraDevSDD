1. Plan

Format: 105 minutes, in person, every participant at their own computer.
Audience: developers who know React and Git; experience with Copilot agent mode at any level, including none.
Running example: the service-centre page «תמונת לקוח 360» (customer profile) — Hebrew UI, RTL, data from the open DummyJSON API.

What a participant takes away

  1. A cycle walked with their own hands: spec → tasks → plan → execution by an agent → independent review → security → build.
  2. An understanding of what a gate is and why approved is set by a human.
  3. Three transferable Copilot skills: use a skill shipped in a repository (/sdd), create a custom agent by analogy (react-engineer), run an independent reviewer agent (/review, /security-review).
  4. A repository with a working page and the full history of decisions under docs/specs/.

Decision: what we show SDD on

Three options were considered.

CriterionThe full spec-development skillOpenSpecWrite a skill from scratch in the room
Fits in 105 minutesNo: 585 lines of rules, 15 templates, an epic of 26 sectionsYesNo: everyone ends up with a different skill and results diverge
Gates and statusesYes, G0–G9No: the project description says outright there are no hard phase gatesWhatever we manage to write
Waves and parallel agentsYesNoNo
Independent review and fix loopYesNoNo
Vocabulary matches the SDD deckYesNo: proposal / design / delta specs—
Installation on participant machinesA folder in the repositoryGlobal package, Node 22.12+, commands depend on the profile—

Choice: a workshop extract of our own skill — sdd, shipped in the repository at .github/skills/sdd/. Same concepts and formats (SPEC-NNN, acceptance criteria, tasks, waves, review.log.md), but one page of rules and six short templates. VS Code picks it up from the folder once the workspace is trusted (chat.useAgentSkills is on in .vscode/settings.json): the participant installs nothing.

Why the implementer agent is created live. The request was "build something ourselves with the tools". In block 2 we create the react-engineer agent after the pattern of workshop/reference/rn-engineer.agent.md. It is the same skill as writing one from scratch, but the result is predictable: the pattern fixes the structure, and the fallback file in workshop/fallback/agents/ insures the block.

Why the reviewer is an agent shipped in the repository. In version 1 the reviewer was installed separately, as a plugin, to stress that it does not belong to the project. Copilot's plugin mechanism lives in Copilot CLI, not in VS Code agent mode, so in version 2 the code-reviewer agent lives in .github/agents/ and is invoked through the /review and /security-review prompt files. Independence now comes from the role, not from the location: the agent has no editing tools (tools: ['read', 'search', 'execute']), it never receives the implementer's hand-off digest, and it re-runs the gates itself. Say this out loud in block 1 and again in block 6.

OpenSpec gets one comparison slide at the end and a link — the same "spec before code" idea, without gates, waves or review. The full skill is handed out after the meeting as the next step; the end of SKILL.md lists exactly what the workshop edition simplifies.

The open API: DummyJSON (/users/{id}, /users/{id}/todos). Not a random pick: together with the profile it returns password, ssn and card data. So the allowlist of response fields is a real spec requirement and the security gate checks a real risk, not a formality.

Facilitator checklist

The day before

  • The repository is pushed to GitHub with the cp/1 … cp/8 tags; on a clean clone npm run catchup lists eight checkpoints without "tag not found".
  • The dry run has been done by the controller on a clean clone; FEEDBACK.md has been read and the after-the-dry-run list is worked through.
  • npm run doctor outputs collected from participants; problem machines sorted out (most often: Copilot extensions missing, no git identity, Node too old).
  • Known whether the room's network reaches dummyjson.com. If not — at every browser step say npm run dev:offline straight away.
  • Known which Copilot plan and model the participants have. The model selected in Copilot Chat drives the speed of block 5; ask people to keep the model the controller used in the dry run (it is recorded in FEEDBACK.md).
  • Your own machine: a clean clone on macOS, VS Code with Copilot signed in, the project opened once and trusted, npm run doctor green.

15 minutes before

  • Open on the screen: the slides (F — full screen), VS Code with the clean clone and the Copilot Chat panel in Agent mode, a second terminal inside VS Code (Ctrl+`⌃`) for npm run dev, a browser, and workshop/prompts.html switched to Windows — that is what the room sees.
  • Editor and terminal font enlarged: a command line must be readable from the last row. The Copilot Chat panel wide enough that a report table fits.
  • On your machine the react-engineer agent is not created — you do block 2 together with everyone. The code-reviewer agent, /sdd, /review and /security-review are present (they come with the repository).
  • An assistant in the room is appointed: they walk the rows, you do not leave the screen.
  • course/rehearsal/reports/06-review1.md and course/rehearsal/screens/ at hand — examples to show if your own review returns APPROVED at once or your page looks different.

What to know in advance

  • The trust dialog is not optional. On first open VS Code asks whether to trust the folder. In restricted mode the agents, skills and prompt files under .github/ do not load and the workspace settings.json is not applied, so every terminal command would ask for approval. Everyone presses Yes, I trust the authors — ideally at home (prework item 4).
  • Two kinds of approval. Terminal commands outside the allow-list show Allow; file edits made by the agent appear as pending changes with Keep / Undo. The gate commands (npm run …, npx vitest, node scripts/) and the git commands the skill uses are pre-approved in .vscode/settings.json. How many prompts actually remain per step is what the dry run measures unverified until the dry run; extend the allow-list from FEEDBACK.md.
  • A new agent file needs a reload to show up. After block 2, if react-engineer is not in the agent dropdown — Developer: Reload Window (Ctrl+Shift+P⇧⌘P), then a new chat.
  • The epic comes out big. In the version 1 rehearsal: 16 acceptance criteria, 333 lines (a different agent, so treat the numbers as an indication). Nobody reads it whole in three minutes at gate G1 — steer the room to the four questions on slide 18.
  • The review finds real things. In the rehearsal: a race condition when navigating customer 1 → 2 → 1 while the second request is still pending. The report is in course/rehearsal/reports/06-review1.md. If your review returns APPROVED at once, show that one and say which agent produced it.
  • /security-review says what it read. The prompt file asks the reviewer to list every changed file and say whether it read it fully. A good moment to say: the verdict covers only what was read.
  • Subagents. The skill launches react-engineer as a subagent of the orchestrator chat, one invocation per task, all in the same turn "so they can run side by side where the harness supports it". Whether Copilot runs them in parallel or one after another is unverified — the dry run will tell; do not promise parallelism on stage until it does. If subagents are not available at all, the skill prints each task prompt and tells the participant to run it in a new chat with react-engineer selected; the fallback boxes of steps 3 and 5 describe this.
  • Memory is in the repository, not in the chat. Every step starts a new chat on purpose; plan.md and review.log.md carry the state. The two exceptions are /sdd fix after /review (same chat, so the orchestrator sees the report) and /sdd close after /security-review (the prompt tells it to take the result from the conversation; if it was run in another chat, paste the result).
  • The page on the screen after wave 3 is in course/rehearsal/screens/. Participants' pages will differ in layout detail; the acceptance criteria are about behaviour.

Before the meeting: after the dry run

A test participant ("the controller") walks the whole workshop before the meeting using workshop/START.html — the same prompts.html, the same prompts, --commit on — and returns workshop/FEEDBACK.md plus a git bundle (git bundle create sdd-dry-run.bundle --all) or a link to a fork. Then, in this order:

  1. Read FEEDBACK.md end to end. Per step: minutes, number of approval prompts, rephrased prompts, errors and agent questions quoted, which fallback box was used and whether it helped. Mark every step the controller rated "worked with changes" or "did not work".
  2. Adjust workshop/prompts.html. Replace prompts the controller had to rephrase with their working version; fix fallback boxes that did not help; add a note wherever the agent asked a question the controller could not answer. Keep the step numbers — the slides and this guide refer to them.
  3. Extend the allow-list in .vscode/settings.json. Every terminal command Copilot asked to allow that is safe and expected (gates, read-only git, the project's Node scripts) goes into chat.tools.terminal.autoApprove. Do not add file-writing shell commands — AGENTS.md forbids them for a reason.
  4. Build the checkpoint tags from the bundle and push them. scripts/catchup.mjs expects exactly these tags: cp/1-agent, cp/2-spec-001-done (both on main history), cp/3-spec-002-docs, cp/4-wave-1, cp/5-wave-2, cp/6-wave-3, cp/7-review-fixed (on the spec/002-customer-profile history, all descending from cp/2), cp/8-spec-002-done (on main). The procedure below is git only, identical in PowerShell and zsh; only the bundle path differs. Terminal — in your clone of the participant repository 
    git bundle verify C:\path\to\sdd-dry-run.bundle~/Downloads/sdd-dry-run.bundle
git fetch C:\path\to\sdd-dry-run.bundle~/Downloads/sdd-dry-run.bundle "refs/heads/*:refs/remotes/dryrun/*"
git log --oneline --graph dryrun/main dryrun/spec/002-customer-profile

    If the controller started from the published main, tag the commits in place: the "chore: add react-engineer agent" commit is cp/1-agent, the merge of spec/001-app-shell is cp/2-spec-001-done, "docs(SPEC-002): epic, tasks, plan" is cp/3-spec-002-docs, the three feat(SPEC-002): wave N commits are cp/4–cp/6, "fix(SPEC-002): review round 1 findings" is cp/7-review-fixed, the merge of spec/002-customer-profile is cp/8-spec-002-done. If the starter changed after the controller cloned it (you edited prompts.html or settings.json in steps 2–3), replay the controller's commits on top of the new main with git cherry-pick and tag the replayed commits — the version 1 rehearsal needed the same replay.

    git tag cp/1-agent <commit>
git tag cp/2-spec-001-done <merge commit>
git tag cp/3-spec-002-docs <commit>

Replace workshop/golden/SPEC-002-customer-profile/ with the controller's generated epic.md, tasks.md, plan.md if they are better than the current reference — that is, if they went through two review rounds to APPROVED and release:check green, and the epic has the allowlist criterion and a non-empty "Out of scope". 3. Three rules for the room

Say them at the start; come back to them at the first failure.

  1. A block ends by the clock. Not done — take the fallback file from workshop/ or a ready checkpoint (npm run catchup -- <number>) and continue with everyone. Finish your own version at home, with the same prompts.html.
  2. Copy from prompts.html, do not retype from the slide. Which prompt to take is written in the bottom-right corner of the slide: prompts.html · step 4 · tasks. The same corner shows the slide range of the current block and the slide number — the same numbers as in this guide.
  3. The agent stopped and is asking — that is not a breakdown. Read the question aloud to your neighbour. Most of the time a gate has fired as designed. The same goes for Copilot's Allow and Keep prompts: read what it wants to run or change, then press.

4. Running the meeting

Per block: what to say, what participants do, what must be on the screens, when to stop the block and what to do when something fails. Timing from the plan. Prompts are in workshop/prompts.html: participants copy from there, the slides only point at the step.

6. If everything goes wrong

The recovery ladder — always from the cheapest rung up. Say it at the first failure and point at it again when someone panics.

  1. The fallback box of the current step in prompts.html. Every step ends with "If it did not work": a copy command for the ready file, a plain-words prompt instead of a slash command, a stop prompt for a red gate, the no-subagents procedure. Thirty seconds, no state lost.
  2. A checkpoint: npm run catchup -- <number>. Moves the project to the finished state after a step (1 agent · 2 SPEC-001 merged · 3 SPEC-002 documents · 4/5/6 waves · 7 review fixed · 8 SPEC-002 merged). The participant's work is kept on a backup/… branch and, if there were uncommitted changes, in git stash. After the jump: a new Copilot chat. Costs a minute; the participant continues with the group from the step the command prints.
  3. The facilitator's screen. The participant watches the step on the projector and does it at home with the same prompts.html. Nobody is left out of the discussion, and the room does not wait.
